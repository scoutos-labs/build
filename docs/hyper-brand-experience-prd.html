1 · Summary & core concept

Build's visual identity today is an unbranded Scout leftover: one 189-line src/styles.css with --scout-* tokens, a font stack naming GeistSans that is never loaded (the app renders system-ui), and a managed-auth boot chain that drops signed-out users into a raw fullscreen Clerk overlay (src/managed-auth.ts:83-116) before the Gleam runtime exists. There is no landing page.

This loop makes Build unmistakably hyper's product, from the first pre-auth pixel to the moment the agent finishes a build turn. Three coherent moves: (1) the hyper brand system (Space Grotesk + PT Mono, azure/ink/base palette); (2) a pre-auth landing whose hero is a real prompt box that carries the typed idea through sign-in into the interview; (3) two competitor-validated building-experience wins — a "Try to fix" card on preview errors and changed-file narration chips on assistant turns.

Signature element (the one aesthetic risk): the amber bolt (#FABA00, hyper's logo mark) becomes Build's working state. Everywhere the app is doing work — thinking pill, preview generation overlay, boot journey — the bolt appears and pulses. Amber means "hyper is building." Everything else stays calm azure/ink. Boldness spent in exactly one place.

2 · Goals / non-goals

GOAL hyper brandkit applied to all Build chrome · GOAL pre-auth landing with prompt carry-through · GOAL Try-to-fix on preview errors · GOAL build-narration chips · GOAL a11y/reduced-motion/responsive quality floor

NON-GOAL design-guidance files (style prompts for generated apps, guard-tested — untouched) · NON-GOAL dark mode · NON-GOAL layout-mode DOM/mechanics changes · NON-GOAL server changes / budget accounting / publish flow · NON-GOAL editing build/ or dist/ output · NON-GOAL deep Clerk-internal re-theming (frame it if theming resists)

4 · Architectural decision — landing page

Pre-auth static TS module (src/landing.ts, pure DOM), invoked from the managed branch of boot() in src/main-gleam.ts, not a Gleam view. Rationale: the boot-gate contract forbids starting the Gleam runtime/WebContainer/IndexedDB pre-auth; styles.css is already loaded pre-boot so the landing shares brand tokens with zero duplication; COOP/COEP (same-origin/require-corp, WebContainers hard requirement) is satisfied by construction with same-origin-only assets (self-hosted fonts, inline SVG bolt); Clerk's redirect OAuth flow is reused unchanged, mounting into a landing-owned slot instead of the bare #signInGate. Prompt carry-through: idea → sessionStorage["build.landing-prompt"] → one-shot post-boot consumption seeds interview/composer → key cleared. Flag-off (non-managed) mode byte-identical in behavior.

5 · Privacy & security constraints (binding)

  • Only credential client-side: VITE_CLERK_PUBLISHABLE_KEY (publishable by design). Gate: grep built dist/ for sk_, CLERK_SECRET, secret env names.
  • No telemetry, no tracking, no cross-origin asset/script/font/telemetry requests pre-auth (fonts self-hosted in public/fonts/, OFL licenses vendored). The only permitted cross-origin traffic is Clerk's existing frontend-API calls, which managed auth cannot function without.
  • Landing prompt is user content: sessionStorage only, never sent pre-auth, never console-logged, cleared after one-shot consumption.
  • ensureSignedIn() token/listener/reload-on-sign-out logic untouched; COOP/COEP headers not relaxed.
  • Try-to-fix consumes only messages passing isTrustedPreviewMessage; error text rendered as text, never HTML.
  • Load-bearing UI constraints: Focus-mode .panel.chat never carries transform/filter; .msg clamp/overflow traps per docs/founders-ux-*.

Step 3 — Pre-auth landing with prompt carry-through

New src/landing.ts per §4; ensureSignedIn restructured minimally (Clerk mounts into landing slot; auth logic byte-identical). Copy: eyebrow BUILD ANYTHING; hero "Create. Connect. Build."; benefit line; prompt box hero + 3–4 specific example chips; sign-in CTA. Seed handshake (reviewer advisory, binding): the bridge sendMsg silently drops messages pre-registerRuntime, and AnswerSubmitted no-ops in Idle; interview eligibility is decided at MessagesReplaced hydration.   • AC: signed-out managed visit → landing, never raw overlay; idea survives OAuth redirect round-trip and pre-fills interview/composer with key cleared; signed-in reload skips landing (no flash — landing renders only after clerk.load() resolves signed-out; pre-load treatment is a minimal branded base-color shell, testable); flag-off byte-identical; keyboard operable; responsive 980px/375px; no cross-origin requests other than Clerk frontend-API; no secrets/console-logged prompt.

Step 4 — "Try to fix" on preview errors

BUILD_PREVIEW_ERROR (already guard-checked in main-gleam.ts) → preview actor last_preview_error: Option(String). Chat renders quiet error card (ink on base, amber left rule) with error text + "Try to fix" button dispatching a prewritten agent prompt embedding the error. Clears on next successful turn or preview reload; disabled while busy.

  • AC: broken app surfaces card within one error event; click sends exactly one agent request containing the error; never appears during interview; clears on recovery; pure Gleam actor test covers transitions; guard tests green.
  • Evidence: npm test incl. new actor test; repro screenshots (broken → card → fixed → gone); diff confirms isTrustedPreviewMessage path.

Step 5 — Build-step narration chips

Assistant bubbles show PT Mono chips of changed file paths, derived from patch paths already persisted to buildLog. Styled on existing .storyChip vocabulary, re-tinted.

Either extend the message type with optional paths (touches persistence in src/projects.ts, has tests) or write documented, tested correlation rules. AC addition: an error bubble between two successful turns must not shift chips.

  • AC: one chip per patched path; chips respect .msg clamp (no overflow-trap regression); zero-patch turns show no chip row; Build Story output unchanged; expand/collapse unchanged.
  • Evidence: npm test; screenshots clamped + expanded; before/after Story export comparison.
